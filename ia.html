What this page settles

Four corrections that came out of building this IA end-to-end — see each section below for the full reasoning.

The entry point is Race browse, not a screen called "Onrace"An earlier draft modeled a distinct entry screen to carry Main Job 2. It never existed as separate UI — removed from the tree and the matrix; its rationale relocated, not deleted (see Navigation in sitemap.md).
Four infrastructure screens, justified by auth, not by a jobSign in / Sign up, Reset password, New password and Profile close no job of their own (formerly tagged "orphan"). The test for them isn't "does a job need this?" but "does the existence of accounts require it?" Sign in / Sign up is a contextual gate; Profile is a global tab (since 2026-09-25). Profile, added 2026-09-25, reverses the earlier "no job supports Profile" verdict. Infrastructure flows of their own: sign-up with email confirmation (Flow 4), profile + sign out (Flow 5), and password reset (Flow 6, 2026-09-25), which adds Reset password and New password as Sign in's recovery path.
Every success endpoint is now a verifiable conditionNot a screen destination. Log Result's success previously just "landed on a screen" — tightened to "a results row now exists with official_result_url populated."
One dead end is a known, accepted MVP gapA logged result's source link can rot with no in-app fix (DeadEnd5). Left as-is on purpose — no job asks to correct a result, only to log or retrieve one. Now tracked in research.md.

Sitemap

Screens, grouped by entity cluster

Grouped by the two entity clusters in sitemap.md — Discovery (Race listing + Search/filter criteria) and Archive (Logged result + Source-link proof) — not by generic "site sections." Every screen carries the job(s) it closes; a plain outline means the close is framing-level, not a dedicated interaction.

App entry: Race browse is the landing screen at 0 taps — see Navigation in sitemap.md. An earlier draft modeled a separate "Onrace — entry" screen for Main Job 2; it never existed as real UI and was removed. The reasoning wasn't wrong, just misplaced — it describes this global nav structure (Discover + My Results as co-equal items), not a screen.

Global navigation — 3 tabs (revised 2026-09-25): Discover → Race browse, My Results → Results list, and Profile → Profile. Log result is no longer a tab: it's the primary action button inside My Results (header, plus the empty state's call to action), because tabs are destinations and actions are buttons. Cost: logging a result goes from 1 tap to 2 from anywhere outside My Results, with no extra sign-in step. Replaces the earlier 3-tab bar (Discover / Log Result / My Results); that reasoning is kept, marked superseded, in sitemap.md → Navigation § 1–2. Profile became a tab on 2026-09-25 for 1-tap consistency and the familiar Account-tab convention. That accepts an auth entry point on every top-level screen, Discover included, though Discover itself gates nothing. It replaces a same-day account button inside My Results. Profile is 1 tap from any top-level screen (2 from Race detail, which has no tab bar), and Sign out is 3 (Profile → Sign out → confirm; the confirm alert is a deliberate extra tap).

Related 4 · Retrieve Social

Sign in / Sign up Infrastructure

No job in jtbd.md calls for account creation or login on its own. Exists because Logged result is owner-only via RLS, so accounts exist. Resolved as a contextual gate — surfaces only when an unauthenticated person taps My Results or Profile (the Log result action lives inside My Results, so that gate covers both archive jobs) — not promoted to a global nav item, not deleted.

Method, decided 2026-09-25: email + password through Supabase Auth, with Confirm email on. Create account doesn't sign anyone in: it leads to a "check your inbox" step, and the emailed link signs them in (Flow 4). Not in MVP: magic links, social sign-in. Password reset, closed 2026-09-25: "Forgot password?" on Sign in opens Reset password (Flow 6) — by the same "does auth require it?" test, email + password needs a way back in. Passwords are at least 8 characters [?], at sign-up and on reset alike.

Reset password Infrastructure

Added 2026-09-25. Ask for a reset link: one email field, then "check your inbox". The copy says "if an account exists…", because Supabase answers the same either way — nobody can use the form to learn who has an account. Not job-sourced; exists because email + password sign-in does (sitemap.md → Entities → 5). Entry: contextual, "Forgot password?" on Sign in only — a drill-down inside the Sign in modal ("‹ Sign in"), no tab bar.

States (Flow 6): loading · couldn't send · too many requests · check inbox.

New password Infrastructure

Added 2026-09-25. Set the new password: New password + Confirm, at least 8 characters [?]. Entry: only by opening the emailed reset link, which starts a short-lived recovery session — no in-app route leads here. Its exits all lead back to Sign in (success, cancel) or to Reset password (expired link).

States (Flow 6): saving · too short / don't match (client) · same as current · couldn't save · link expired (no form: request a new link). Success: password changed, recovery session ended on this device, back on Sign in with "Password changed" to sign in with it.

Profile Infrastructure

Added 2026-09-25. Shows whose account this is and lets the person leave it: initials (photo deferred until Supabase Storage is decided), name, country, language [?] (stored preference only, no localization yet), and Sign out. No bio, stats, or public view. Entry: the Profile tab, one of 3 global tabs. Signed out, it opens the same Sign in / Sign up gate as My Results. Reverses the 2026-09-24 "no job supports Profile" verdict: that asked whether a job needs it, the wrong test for infrastructure. The right test is whether accounts require it. See sitemap.md → Entities → 5.

States (2026-09-25, Flow 5): loading · couldn't load · a field's change didn't save (fields save as they change; a failed save reverts inline). Sign out asks first (confirm alert), then signs out this device only — a local session clear, no network call — and lands on Race browse.

Decisions

  • BranchAny races match current filters? — results vs. empty state.
  • RetryRace-list fetch failure — retry or give up.
  • RetryRace-detail fetch failure — same choice, one level down.
  • ResolvesWorth entering? — where "compare them in one place" resolves into a decision.
  • Lightweightregistration_url present and well-formed, and new tab not blocked? — reworded 2026-09-24 from "Registration link opens?": a browser can't see whether the organiser's site loads in another tab, only whether the link was usable and the tab opened. Two direct edges, no retry diamond. registration_url is Onrace's own curated, manually-seeded data (low rot risk); official_result_url is arbitrary user-submitted data (high rot risk) — that asymmetry, not job importance, is why this check is lighter than Retrieve Proof's.

States

  • Loading: fetching races (list) · fetching race details (single race, own step).
  • Empty: no races match the current filters.
  • Error: could not load races · could not load race details · couldn't open registration link (missing/malformed URL, or new tab blocked).

Endpoints

Success A new tab has opened on the race's registration_url — the entire condition, and all Onrace can verify; whether the organiser's site then loads is outside its view. No Onrace-side record is created; unlike the other two flows, this endpoint isn't verifiable from Onrace's own data — completion happens entirely on an external site.
Dead end — DeadEnd1 Leaves without deciding on a race. One merged outcome from three causes (empty result, failed list fetch, failed detail fetch) — same downstream reality, no race decided on.
Dead end — DeadEnd6 Decided to enter, but couldn't open the registration link (missing/malformed URL, or new tab blocked — Onrace can't know the link is broken, only that it couldn't open it). Kept separate from DeadEnd1 on purpose — this person already decided; the failure is discovered after that, not indecision.

Decisions

  • GateSigned in? — logged results are owner-only via RLS, so the My Results tab gates into Sign in / Sign up, a contextual gate. A successful sign-in lands on Results list. (The same gate is also reached from the Profile tab; that path lands on Profile and is Flow 5, not this one.)
  • ReferenceCreates an account instead → Flow 4, drawn once and referenced ([[...]]), not redrawn here. A confirmed sign-up lands on Results list.
  • ReferenceForgot password → Flow 6 (added 2026-09-25), also referenced, not redrawn. A changed password returns to Sign in, where the person signs in with it; the reset itself never lands on Results list.
  • BranchSign-in succeeded? — a third edge since 2026-09-25: "email not confirmed yet" (Supabase's distinct error) routes into Flow 4's check-your-inbox step, not the generic sign-in error. Retrying can't fix it; confirming the email can.
  • [?] FlaggedFinds and taps Log result? — the form is one in-page action away from Results list (header button or empty-state call to action), not a tab. Rests on the unvalidated hypothesis that people look for logging inside My Results. The action must stay usable while the list is loading or has failed to load.
  • CatalogAny past races match the search? (Race picker, added 2026-09-25) — optional "Find in race catalog" searches only races whose event_date has passed. No match isn't an error: change the search or type the race in. Picking a race fills and locks race_name/date/sport_type; cancelling leaves the form unchanged.
  • RetryCatalog failed to load — "no" isn't a dead end: the form works without a catalog link, so giving up on the picker means typing the race in.
  • Requiredofficial_result_url filled in? — the one field CLAUDE.md explicitly marks "(required)"; enforces the source-link trust model before submission.
  • [?] Flaggedrace_name/date/sport_type/finish_time all filled in? — a second, separate check. CLAUDE.md's data model just lists these fields, it doesn't say they're required — modeled here as an assumed requirement, flagged per this document set's own convention, not settled fact. The first three come from the listing when a catalog race is linked.
  • RetryFix and resubmit? — offered separately after each validation failure, and after a failed submission.

States

  • Loading: signing in · fetching past catalog races (Race picker, on open and on each search) · saving result.
  • Empty: no catalog race matches (Race picker).
  • Error: sign-in failed · could not load the race catalog · source link is required · required field missing [?] · couldn't save the result (was "link unreachable / submission failed" until 2026-09-25: a client-side app can't check that an arbitrary timing site is reachable, only that the save failed).

Endpoints

Success — Success2 A new row now exists in results, owned by this user via RLS, with official_result_url populated — the field CLAUDE.md requires — plus race_name/date/sport_type/finish_time per this flow's [?]-flagged check, and the catalog race linked if one was picked. Tightened from "lands on Results list," a screen, not a condition.
Dead end — DeadEnd2 Leaves without logging the result. Reachable from a failed sign-in (after retries) or closing Sign in / Sign up without attempting. Root cause: never got signed in.
Dead end — DeadEnd7 [?] Reached My Results, never found Log result. Signed in, right screen, but never took the in-page action. Root cause: the action wasn't findable enough; fix: its placement/prominence. Added 2026-09-24 with the 2-tab nav, flagged as untested.
Dead end — DeadEnd3 No result saved, proof lost for later. Reachable from the source-link check, the other-fields check [?], or the save itself failing — a forms/data problem, once already past sign-in. (Race picker failures don't lead here: every picker exit returns to the form.)

Decisions

  • BranchRequest accepted? — the only thing Onrace learns from the request. "Yes" means Supabase took it, not that an email went out: Supabase answers the same for addresses with no account, so the form can't be used to find out who has one. "Too many requests" is Supabase's rate limit on auth emails, a distinct answer whose fix is waiting, not retrying at once.
  • BranchReset link valid? — checked when the app opens with the link. Like Flow 4's confirmation links, reset links expire and work once.
  • [?] FlaggedAt least 8 characters, and both fields match? — client-side, before anything is sent. 8 is Onrace's choice (a Supabase project setting; its default is 6), flagged because nothing in the docs sets it yet. The same minimum should apply at sign-up.
  • BranchPassword updated? — two server-side "no"s with different fixes: a password identical to the current one (choose another), or a connection failure / expired recovery session (retry, or request a new link).
  • ObservabilityWhat Onrace can and can't see, stated the same way as the registration-link check. It can know whether Supabase accepted the request. It can't know whether an email arrived, whether an account exists, or whether the link is ever opened — that happens in someone's inbox, so Check inbox says "if an account exists…". It can know again once the link is opened: whether it's still valid, and whether the new password saved.

States

  • Loading: sending reset link · saving new password.
  • Check inbox: open the reset link, only sent if an account exists — a step waiting on the inbox, the same kind as Flow 4's, with its own state page (wireframes/_conventions.md § 4). Drawn in the empty-state color, like Flow 4.
  • Error: couldn't send the reset link (connection) · too many requests — wait a minute (rate limit) · reset link expired or already used · too short, or the two passwords don't match (client-side, inline) · that's your current password — choose a different one (server-side) · couldn't save the new password.

Endpoints

Success — Success6 The password is changed, then Onrace ends the recovery session on this device (local sign-out) and returns to Sign in with a "password changed" line. Supabase would leave the person signed in; Onrace deliberately doesn't — signing in once with the new password proves they know it, and next carries them where they were heading. Verifiable as: the password was updated, and no session exists on this device.
Dead end — DeadEnd11 Leaves without a reset link — the request itself failed or was rate-limited, and the person gave up. Onrace saw it happen.
Dead end — DeadEnd12 Reset never completed — a request was accepted, but no new password was set: no account for that address, a lost email, an expired link, or giving up on the form. Onrace can't tell most of these apart by design (the anti-enumeration answer and the inbox are outside its view), which is why it's one node, not four.
