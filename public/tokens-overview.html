The two levels, the rules, where they live CLAUDE.md → Tokens

The two levels:

  • Primitives: raw values with no role in their names. Colors are named by hue and lightness (CIE L*, rounded): --graphite-7 is the gray at L* 6.69, --amber-78 the amber. Every other value keeps a scale or part name (--space-4, --radius-2, --target, --bar-title-inset).
  • Semantic roles: color only (and one opacity, --opacity-disabled). Each role is a var() of a primitive, with a comment naming the usages it grew from (--page, --surface, --text-primary, --accent-fill, --accent-ink, --error, --map-water …). A role is split wherever its uses would need different values in another appearance; the light theme is the test.

Where they live:

  • design-system/tokens/tokens.css: both levels, the Dynamic Type, reduced-motion and Reduce Transparency overrides, the light block (:root[data-theme="light"], roles only), and, at the end, a generated comment with every role pair's contrast in both themes.
  • design-system/components/: one file per component, reading roles and primitives through var().
  • design-system/components/index.css: those files bundled in cascade order by scripts/build_components.py.
  • design-system/index.css: the entry point, generated by scripts/build_components.py: tokens/tokens.css, then components/index.css, in one file (Lesson 9 step 1); it is what a page links.
  • design-system/map-data.css: the static map's generated data (Natural Earth masks, --map-ratio, each pin's place), written by scripts/concept/build_map.py, linked only where the map shows.
  • design-system/tokens/theme.js: turns ?theme=light into <html data-theme="light"> and keeps it for the tab.
  • A page links design-system/index.css (plus design-system/map-data.css on Race browse and the showcase) and design-system/tokens/theme.js.

The rules:

  • Color only through roles: no component reads a color primitive.
  • Geometry from primitives: radius, spacing and size come from tokens, never a number in a class. The only numbers left are math inside calc(): a sign, a half, and a count of a primitive, the last only as a named primitive's definition in design-system/tokens/tokens.css (build check 16).
  • No hex, px or font name in a component, no named or functional color (black, white, rgb()), and no fixed color-scheme.
  • Hex lives in one file: DESIGN.md's frontmatter values and .impeccable/design.json are generated from design-system/tokens/tokens.css (scripts/build_design_sidecar.py).

The build checks that enforce them (scripts/concept/build_stand.py, see UI assembly → Checks that stop the build):

  • build_components.py: no primitive, hex, px, font name, named color or fixed color-scheme in a component.
  • Color rules 1–3: 1 and 2 in both themes, 3a dark only, 3b reported for both themes' fill and ink.
  • Contrast: every pair and every glass pair in both themes.
  • Signed tokens: every token in design-system/tokens/tokens.css, design-system/map-data.css and the docs layer has a row on the stand.
  • check_kit.py: every screen on tokens and components, every class defined.
  • check_links.py: no page links a missing file.
  • Counts are named: a value like three targets is a named primitive defined in design-system/tokens/tokens.css as --bar-title-inset: calc(var(--target) * 3) with its reason, so it follows --target; a component reads var(--bar-title-inset) and never writes the count itself.

The "keep it" rule (UI assembly; revised 2026-11-06): a value change goes into the token of the right level, a primitive or a role (both themes for a role), never into a component; a component change goes into design-system/components/ and its docs section, then every screen where it stands; a new composition goes into design-system/patterns/. See Contributing to the system.

No styling framework (designer, 2026-11-01): plain CSS by hand, the values in design-system/tokens/tokens.css and one file per component in design-system/components/; no Tailwind, CSS-in-JS, preprocessor or token pipeline. The point is to understand how tokens, components and themes work (concept/concept.md → No styling framework). For Lesson 12, to consider and not decided: common namespaces (--color-, --space-, --radius-, --typescale-) for handoff and Figma variables.

The reference: every token, rendered from design-system/tokens/tokens.css on each build, is on the Lesson 08 overview (scripts/tokens_reference.py): color primitives as hue ladders with the roles that read each one in both themes, the other primitives with a visual sample, the semantic roles in both themes with their source comments, and every contrast pair. The kit showcase (ui/kit.html) has its own Light / Dark switch.

The light theme is a proof only (designer, 2026-10-30): the product stays dark-only (C5). The light block isn't offered to users and won't be polished. The viewer's Light / Dark control stays for the course, and the build keeps checking light, so a component that bypasses the roles is caught. Step 5 found two such holes and fixed them in the components.

1. Value drift: one role, different values

  1. Hover and pressed fills step by different amounts.
    • A raised control (bg-2) goes one level up to bg-3 on hover, pressed or open: .filters-trigger:hover, .chip:hover, .secondary-btn:hover, .filters-trigger[aria-expanded], .view-btn[aria-pressed], .map-pin:hover > span, the alert and action-sheet buttons on hover.
    • A row on a surface (bg-1) goes one level up to bg-2: .row--check:active, a.row--nav[href]:hover, .signout:hover.
    • A card on a surface (bg-1) jumps two levels to bg-3: .race-card:has(.card-link:active), .result-card .card-link:active.
    • So "pressed" means +1 level on rows and +2 on cards. There's no pressed or hover token: each rule picks a level by hand.
  2. The chip family has three heights:
    • --chip-height 24 (format chip, .sport-tag);
    • --filter-chip-height 32 (filter chip, .chip);
    • --pin-h 22 (map pin label, styled like a chip: bg-2, --size-label).
    • These are three components, so the gap may be intended. It's recorded because the pin label reads as the same small tag as the format chip, at 22 against 24.
  3. Body and meta have the same size, under two names.
    • --size-body and --size-meta are both calc(15 * var(--type-unit)). Meta was 14 until C3 raised it.
    • Every element sized 15 has to choose one of the two names, and nothing distinguishes them.
  4. The radii are spread across eight tokens with two scales.
    • Content uses fixed px: --radius-1 4, --radius-2 6, --radius-3 12.
    • iOS shapes use other values: --radius-sheet 38, --radius-alert 34, and the capsules --radius-bar-control, --radius-filter-chip and --radius-tabbar, each written as height ÷ 2.
    • --radius-avatar is 50%.
    • All three capsule tokens express the same role: a capsule is half its own height.
  5. Two tokens serve a role they weren't named for.
    • --focus-ring (2px) is the focus outline width, and it's also the width of the invalid ring (the .rows li:has([aria-invalid]) ring sides).
    • --leading-body (1.45) is a line height, and it's also a vertical spacing unit (margin-block on .sort-toggle, .form-alert .alert-link and two skeleton bars).
  6. The display size is shared by two different things. --size-day (30) sizes the race card's date day and also the Profile initials. An avatar letter and a date figure are different roles that happen to share a size.
